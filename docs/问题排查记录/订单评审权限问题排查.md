## 问题描述

**问题现象：**
- 用户 `xiaojingli` 角色为 `SALES_MANAGER`
- 销售订单评审节点要求角色为 `SALES_MANAGER`
- 用户点击"通过"按钮时，提示"您当前没有权限审批此节点"
- 即使角色匹配，仍然无法审批

**发生时间：** 2025-12-12

**影响范围：** 销售订单多部门评审流程中的销售部门评审节点

## 根本原因分析

### 1. 前端权限检查逻辑问题

**问题：**
- 前端 `canApproveCurrentNode` 函数依赖 `reviewStatus` 状态
- 在点击审批按钮时，`reviewStatus` 可能还未更新
- 前端逻辑判断时机不正确

**代码位置：** `frontend/src/pages/sd/SalesOrderList.tsx:202-230`

### 2. 后端权限检查逻辑不完善

**问题：**
- `get_sales_order_review_status` 函数中，如果 `status_data` 为空或没有 `current_node`，无法进行权限检查
- 缺少备用逻辑，无法从 `workflow_instance` 直接获取 `current_node_id`
- 调试信息不够详细，难以定位问题

**代码位置：** `backend/api/routers/sd.py:1391-1447`

### 3. 角色比较逻辑

**问题：**
- 虽然已经做了字符串类型转换，但在某些情况下 `status_data` 可能为空
- 没有处理 `status_data` 为空的情况

**修改文件：** `frontend/src/pages/sd/SalesOrderList.tsx`

- 在点击审批按钮时，先设置 `selectedOrder`，确保 `reviewStatus` 能正确获取
- 添加详细的调试日志，包括 `can_approve` 值、`debug_info` 内容等
- 改进错误提示，显示更详细的调试信息

**关键代码：**
```typescript

if (statusData && canApprove) {
  openApprovalModal(record)
} else {
  // 显示详细的错误信息

    ? `当前用户角色: ${statusData.debug_info.current_user_role}, 节点要求角色: ${statusData.debug_info.node_approver_role}, can_approve: ${statusData.debug_info.can_approve}`
```

## 常见问题

### Q1: 为什么角色匹配但还是无法审批？

**A:** 可能的原因：
1. `status_data` 为空或没有 `current_node` 字段
2. 前端没有正确使用后端返回的 `can_approve` 标志
3. `reviewStatus` 状态未及时更新

**解决方法：**
- 查看后端日志，确认 `status_data` 和 `current_node` 是否存在
- 查看前端控制台，确认 `can_approve` 的值
- 确保在点击审批按钮时，先调用 `fetchReviewStatus` 获取最新状态

### Q2: 如何确认工作流节点定义正确？

**A:** 执行以下 SQL 查询：
```sql
SELECT 
    wn.node_id,
    wn.node_name,
    wn.approver_role,
    wn."order"
FROM workflow_nodes wn
WHERE wn.workflow_id = 'SALES_ORDER_REVIEW'
ORDER BY wn."order";
```

**预期结果：**
- 第一个节点：`node_id = 'SALES_REVIEW'`, `approver_role = 'SALES_MANAGER'`
- 第二个节点：`node_id = 'ENGINEERING_REVIEW'`, `approver_role = 'ENGINEER'`
- 第三个节点：`node_id = 'MATERIAL_REVIEW'`, `approver_role = 'WAREHOUSE'`
- 第四个节点：`node_id = 'FINANCE_REVIEW'`, `approver_role = 'FINANCE'`

### Q3: 如何重新创建工作流定义？

**A:** 如果工作流定义丢失或损坏，可以：
1. 运行 `backend/create_workflow.py` 脚本
2. 或者在 `backend/init_db.py` 中重新初始化

## 总结

这个问题主要是由于：
1. **前端权限检查逻辑不完善** - 没有优先使用后端返回的权限标志
2. **后端权限检查缺少备用逻辑** - 没有处理 `status_data` 为空的情况
3. **调试信息不足** - 难以快速定位问题

**解决方案：**
- 前端优先使用后端返回的 `can_approve` 标志
- 后端添加备用逻辑，从 `workflow_instance` 直接获取 `current_node_id`
- 增强调试信息和日志输出

**经验教训：**
- 权限检查应该以后端为准，前端只做展示
- 添加详细的调试信息，便于快速定位问题
- 添加备用逻辑，处理异常情况
- 记录问题排查步骤，提高排查效率
