# DIERP 下一阶段收敛计划
## MRP/MPS 计划闭环 + 可切换后端工程化准备

| 项目 | 内容 |
|---|---|
| 文档定位 | MVP 之后的下一阶段执行计划 |
| 核心策略 | 不急着铺 APS/成本/QMS，先把 P0 的 MRP/MPS 计划闭环做成可演示、可验收版本 |
| 工程目标 | 完成从纯前端 mock 到“可切换后端”的工程化准备，避免技术债后移 |
| 建议周期 | 4 周（可按团队规模压缩到 3 周或拉长到 5–6 周） |
| 验收方式 | 客户/评审可稳定演示完整计划链路；页面层不直接依赖 localStorage |

---

## 1. 决策摘要

下一阶段不追求“大而全”的制造 ERP 功能铺开，而是聚焦一条主线：

> **销售订单/预测 → MPS → MRP 净需求 → 计划生产/采购订单 → 确认下达 → 齐套/缺料 → 演示验收**

同时完成一项工程化准备：

> **把 localStorage 读写收敛到 service 层，定义 mock/真实后端可切换的接口，为后续接后端留出干净切口。**

这样做的目的：

1. 继续给客户/评审演示“计划驱动”的制造 ERP 核心价值；
2. 不让 APS、成本、QMS 等复杂模块提前稀释第一迭代；
3. 不在页面层继续堆 localStorage 逻辑，避免后续切后端成本过高；
4. 用可解释的 MRP 结果建立系统可信度，而不是只做业务记录。

---

## 2. 为什么先不做 APS / 成本 / QMS

| 模块 | 暂缓原因 | 前置条件 |
|---|---|---|
| APS 有限产能排程 | MRP 计划订单尚未闭环，排程缺少稳定输入 | MRP 计划订单确认/下达稳定 |
| 制造成本核算 | 领料、报工、费率数据口径尚未完整 | 工单执行数据与费率数据可用 |
| 完整 QMS | 质量检验尚未成为计划与执行的硬约束 | 工单/批次/检验节点数据完整 |
| EAM | 设备产能尚未进入排程约束 | APS 需要设备/停机数据 |
| 业财一体化 | 成本核算未稳定 | 成本归集与差异分析可用 |

结论：**先把“计划闭环”做成可演示资产，再按“计划 → 排程 → 质量/设备 → 成本 → 业财/供应链”的节奏推进。**

---

## 3. 阶段目标

### 3.1 业务目标

在现有 MVP 上补齐最小计划闭环，使系统能够回答：

- 需要生产什么、生产多少？
- 什么时候需要开始生产/采购？
- 现有库存、在途、在制能否满足？
- 缺什么料、缺多少、最早什么时候齐套？
- 哪些计划订单需要确认、下达或调整？
- 每个计划订单的来源和扣减依据是什么？

### 3.2 工程目标

- localStorage 读写收敛到 `services/` 层；
- 页面层不直接调用 localStorage；
- 定义 `planningService`、`inventoryService`、`orderService` 等接口；
- 保留 `VITE_MOCK` 开关，mock 实现与真实 HTTP 实现接口一致；
- MRP 运算写成纯函数，输入/输出可序列化，便于后续搬到后端或 Web Worker；
- 为后续切换真实后端预留适配层，不在本阶段强上后端。

---

## 4. 范围边界

### 4.1 本阶段做

1. 物料计划参数：计划类型、提前期、批量规则、安全库存、MOQ、整数倍、默认供应商/工作中心；
2. 可用量统一口径：现有库存、已分配、在途采购、在制工单、安全库存；
3. 轻量 MPS：按周/日汇总销售订单与预测，支持人工调整；
4. MRP 净需求运算：多层 BOM 展开、净需求计算、计划生产/采购订单建议；
5. 计划订单列表：筛选、排序、批量确认、下达、取消；
6. 计划订单转正式生产订单/采购申请记录（演示级）；
7. 来源追溯：计划订单 → MRP 运行 → 需求来源；
8. 齐套分析与缺料清单；
9. MRP 异常清单：逾期、短缺、建议提前/推迟、安全库存触发；
10. 演示数据扩充：3 层 BOM、多交期订单、缺料场景；
11. service 层抽象与 mock/真实接口切换准备；
12. 10–15 分钟端到端演示脚本。

### 4.2 本阶段不做

- APS 有限产能排程、甘特图、插单模拟；
- 完整 QMS（IQC/IPQC/FQC/OQC、不合格品闭环）；
- EAM 设备台账、点检、故障、OEE；
- 标准成本、实际成本归集、差异分析；
- 完整应收应付、总账、自动凭证；
- SRM 在线协同、WMS 条码/库位/波次；
- 替代料、多工厂、多组织、多币种等高级能力。

## 7. 关键口径设计

### 7.1 可用量统一公式

所有看板、MRP、齐套分析必须使用同一公式：

> 可用量 = 现有库存 − 已分配/预留 + 在途采购（按预计到货日） + 在制工单（按预计完工日） − 安全库存

要求：

1. 公式封装在 `inventoryService.getAvailability(materialId, asOfDate)`；
2. 页面不得自行拼接口径；
3. MRP 按需求日期滚动计算，不使用单一静态可用量；
4. 齐套分析展示缺口时，必须注明扣减了哪些库存/在途/在制。

### 7.2 MRP 计算步骤

1. 收集独立需求：销售订单 + 预测 + 安全库存触发；
2. 按物料和需求日期汇总毛需求；
3. 按低层码从低到高逐层展开 BOM；
4. 对每个物料按日期滚动计算净需求；
5. 净需求 > 0 时，按批量规则调整建议数量，按提前期倒推开始日期；
6. 生成计划生产订单或计划采购订单；
7. 计划生产订单作为下层物料的毛需求继续展开；
8. 输出计划订单、缺料、异常和运行日志。

### 7.3 计划订单状态机

> 建议 → 已确认 → 已下达  
> 建议/已确认 → 已取消

规则：

1. 只有“建议”状态可批量确认；
2. “已确认”可下达，生产类生成正式生产订单，采购类生成采购申请记录；
3. 已下达计划订单保留来源追溯，不允许直接删除；
4. 取消需记录原因；
5. 重跑 MRP 不覆盖已确认/已下达计划订单，只生成新增建议。

## 8. 工程化准备：从 mock 到可切换后端

### 8.1 目标

当前纯前端 localStorage 可继续用于演示，但页面层不得直接读写 localStorage。本阶段不强制上真实后端，但必须完成接口抽象和适配层准备。

### 8.2 建议接口

- `PlanningService`
  - `getPlanningParams(materialId?)`
  - `savePlanningParam(param)`
  - `runMrp(params)`
  - `getPlannedOrders(filter)`
  - `confirmPlannedOrders(ids)`
  - `releasePlannedOrders(ids)`
- `InventoryService`
  - `getAvailability(materialId, asOfDate)`
  - `getShortageByOrder(orderId)`
- `OrderService`
  - `createProductionOrderFromPlanned(plannedOrderId)`
  - `createPurchaseRequestFromPlanned(plannedOrderId)`

### 8.3 切换策略

1. 保留 `VITE_MOCK` 开关；
2. mock 实现走内存/localStorage；
3. 真实实现走 HTTP；
4. 页面只依赖接口，不感知底层实现；
5. MRP 运算写成纯函数，输入/输出可序列化；
6. 后续可把 MRP 纯函数搬到后端或 Web Worker，不改页面逻辑。

### 8.4 工程验收

- 页面层不直接调用 localStorage；
- 切换 mock/真实实现的改动点集中；
- MRP 运算可独立测试；
- 计划订单、可用量、齐套分析共用同一 service 口径。

## 10. 验收标准

1. 可维护物料计划参数，且参数影响 MRP 结果；
2. 可基于销售订单/预测生成 MPS，并人工调整；
3. 可运行 MRP，生成计划生产订单和计划采购订单；
4. 每个计划订单可追溯来源、BOM 层级、扣减依据；
5. 计划订单可确认、下达、取消，生产类转正式工单，采购类转采购申请记录；
6. 可按工单/计划订单做齐套分析，输出缺料清单和最早齐套日期；
7. MRP 异常清单可分类筛选；
8. 演示数据覆盖 3 层 BOM、2 个以上缺料场景；
9. 页面层不直接依赖 localStorage，service 层可切换 mock/真实接口；
10. MRP 运算为纯函数或独立模块，输入/输出可序列化；
11. 形成 10–15 分钟端到端演示脚本，评审可稳定复现。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| MRP 口径不统一 | 结果不可信，返工 | 先写 1 页口径说明，统一 service 实现 |
| 演示数据太少 | MRP 结果无说服力 | 第 1 周即扩充 3 层 BOM 与缺料场景 |
| 页面直接读写 localStorage | 后续切后端成本高 | 本阶段强制 service 层收口 |
| 计划订单与正式工单重复 | 数据混乱 | 明确状态机与来源字段，重跑不覆盖已确认 |
| 范围膨胀到 APS/成本 | 第一迭代失焦 | 本阶段明确不做 APS、成本、QMS、EAM |
| 批量规则过于复杂 | 开发延期 | 先支持逐批、固定批量、最小/最大、整数倍四类 |

## 13. 立即启动的 3 件事

1. **定 MRP 运算口径**：可用量公式、批量规则、提前期、工作日历，形成 1 页设计说明；
2. **扩演示数据**：先造 3 层 BOM、多交期销售订单和 2 个缺料场景；
3. **抽 service 层**：在加 MRP 前把 localStorage 读写收口，避免计划模块继续堆在页面里。

---

## 14. 一句话总结

> 下一步先做“MPS → MRP → 计划订单 → 确认下达 → 齐套/缺料”的最小计划闭环，同时完成 service 层抽象和演示数据扩充；APS、质量、设备、成本、业财与供应链协同放到后续阶段，按“计划 → 排程 → 质量/设备 → 成本 → 业财/供应链”的节奏推进。
