# ERP 订单·库存·资金三线打通计划

> 版本：v1.0 · 2026-11-19
> 目标：覆盖采购、销售、库存、应收应付、成本核算与财务总账，打通**订单、库存、资金**三条主线，让经营数据一体贯通。
> 方法：延续既有工程纪律——**本体驱动**（mappings.json → planning.yaml → generate_models → TTL/SHACL → 应用层）、mock 双端同构、种子幂等、每批全门禁后提交。

---

## 一、现状盘点：两通一断

| 主线 | 已贯通 | 断点 |
|---|---|---|
| 订单线 | 报价（多级审批）→ 销售订单 → MRP → 计划订单 → PR → PO → 收货 → 工单 → 报工 → 完工入库 | **完工之后断**：无发货/出库，订单状态到不了 SHIPPED/DELIVERED |
| 库存线 | 领料扣减、到货回冲、退货、完工入库、可用量（在途/已分配）、流水账本 | 出库侧缺**销售出库**；无盘点、调拨、批次效期 |
| 资金线 | 仅 AP 只读视图（到货金额 − 已结 − 退货冲减） | **应收（AR）整体缺失**；应付无发票/付款核销；**总账缺失** |

**枢纽判断**：三线贯通的枢纽是「业务单据 → 会计凭证」的**自动分录引擎**——没有它，应收应付只是并列孤岛。

**关键结构事实**（影响设计）：`sales_orders` 为**单行结构**（一单 = 一个产品 + 数量 + 金额），因此发货单/发票按**单据级**设计，无需行表，与销售订单结构对称。

---

## 二、总体设计原则

1. **本体驱动全链路**：每个新域先改 `ontology/src/mappings.json`（枚举）→ `ontology/model/planning.yaml`（实体，全字段带 comment 保证 Alembic 零漂移）→ `generate_models.py` → TTL/SHACL/demo.ttl 同步 → `validate-type-sync.js` + `validate-consistency.py` 双绿后才写应用层。
2. **双端同构**：mock handlers + snapshot 与后端同口径；parity 脚本扩项；`check:mock-rbac` 保持绿。
3. **账本即事实源**：所有库存/资金变动写 `material_transactions`（库存）与凭证（资金）；供应商绩效、账龄等指标一律从账本计算，不另设冗余字段。
4. **状态机显式化**：每张新单据的状态枚举进 mappings.json，SHACL `sh:in` 锁定（顺序与 mappings 一致，Check2 敏感）。
5. **每批自验收**：新增 smoke 一律「开头幂等 reset + 尾部自清理」，多冒烟顺序执行互不污染。

## 三、P0 批次：发货出库 + 销售发票 + 应收台账（订单线收口，资金线 0→1）

### 3.1 本体建模（planning.yaml 新增 3 实体，枚举 3 组）

| 实体 | 表 | 顶层范畴 | 关键字段 |
|---|---|---|---|
| `SalesDelivery` 发货单 | sales_deliveries | Document | delivery_number(唯一,DK 前缀)、sales_order_number(FK sales_orders)、customer_id/customer_name、material_code、quantity、unit、unit_price、status(DeliveryStatus)、ship_date、delivery_date(签收)、remarks |
| `SalesInvoice` 销售发票 | sales_invoices | Document | invoice_number(唯一,INV 前缀)、sales_order_number(FK)、delivery_number(FK,可空)、customer_id/customer_name、amount、currency、status(InvoiceStatus)、invoice_date、due_date(按订单交付期或客户条款)、received_amount(默认0，P1 核销用)、remarks |
| `ReceivableEntry` 应收流水 | receivable_entries | EventRecord | entry_number(AR 前缀)、invoice_number(FK)、customer_id、entry_type(INVOICE/RECEIPT/ADJUST)、amount(正开票/负收款)、entry_date、reference_number、remarks |

**枚举**（mappings.json v1.2.0）：
- `DeliveryStatus`: DRAFT / SHIPPED / DELIVERED / CANCELLED
- `InvoiceStatus`: DRAFT / ISSUED / PARTIALLY_PAID / PAID / CANCELLED
- `ReceivableEntryType`: INVOICE / RECEIPT / ADJUST

> 设计取舍：应收以「发票 + 应收流水」承载（开票 INVOICE、收款 RECEIPT 各记一笔流水），P1 收款核销只追加流水行并回写发票 `received_amount`——账本口径与库存流水一致。

### 3.2 状态机与业务规则

```
发货单：DRAFT --ship--> SHIPPED（出库扣成品库存 + 记 SALES_ISSUE 流水）--deliver--> DELIVERED（签收）
        DRAFT/SHIPPED --cancel--> CANCELLED（SHIPPED 取消需先红字冲回出库）
发票：  DRAFT --issue--> ISSUED（生成 AR 流水 INVOICE；校验发货单已 SHIPPED）
        ISSUED --(P1 收款核销)--> PARTIALLY_PAID / PAID
校验：  Σ发货量(非CANCELLED) ≤ 订单 quantity（超发 400）；Σ开票金额 ≤ Σ已发货量×单价（超开 400）
联动：  全量发货 → 销售订单 status 置 SHIPPED（复用既有枚举值）；签收置 DELIVERED
```

### 3.3 后端端点（`backend/api/routers/sd.py` 新增或独立 `delivery.py`——按既有风格并入 sd 域，走 sd 写权限门）

- `GET /sd/deliveries`（列表+过滤 customer_id/status/order_number）、`GET /sd/deliveries/{n}`
- `POST /sd/deliveries`（创建 DRAFT；校验订单存在、可发余量，两阶段校验后落库）
- `POST /sd/deliveries/{n}/ship`（出库：扣 `Material.current_stock` + 记 `material_transactions`（type=SALES_ISSUE, ref=SALES_DELIVERY）；订单状态联动）
- `POST /sd/deliveries/{n}/deliver`（签收）、`POST /sd/deliveries/{n}/cancel`
- `GET /sd/invoices`、`GET /sd/invoices/{n}`、`POST /sd/invoices`（挂发货单，校验已发货+金额上限）
- `POST /sd/invoices/{n}/issue`（确认开票 → 写 `receivable_entries`(INVOICE) → 发票 ISSUED）
- `GET /sd/receivables`（应收台账：按客户聚合 发票额/已收/未收/账龄分段——P0 先出账龄，核销 P1）
- 数量/金额聚合一律从发货单/发票表反查（**不给销售订单加列**，避免动既有托管表）

### 3.4 前端（2 新页 + 1 扩展）

| 页面 | 路由 | 内容 |
|---|---|---|
| 发货管理 | `/sd/deliveries` | 列表（状态 Tag）+ 新建（选可发货订单，余量校验）+ 发货/签收/作废 |
| 销售发票 | `/sd/invoices` | 列表 + 新建（挂已发货单，金额上限）+ 确认开票；发票 ISSUED 后显示应收状态 |
| 应收台账 | `/sd/receivables` | 按客户聚合（开票额/已收/未收/账龄 30/60/90+），下钻发票明细 |

菜单：「销售与分销」分组加 3 项（该分组现 4 项 → 7 项，可接受）。

### 3.5 mock / 种子 / parity

- mock：deliveries/invoices/receivables 全套路由 + 收发货写流水；snapshot v14 加 3 集合 + 2 张演示发货单（1 DRAFT / 1 SHIPPED）+ 1 张已开票发票；种子 `seed_sales_delivery_demo`（备注标记幂等）。
- reset：3 张新表入清理列表；种子里 1 张 SHIPPED 单需在种子时**同步扣库存并写流水**（保证 reset 后库存与流水自洽）。
- parity 扩项：发货单(客户/状态/数量)、发票(客户/状态/金额)、集合结构。

### 3.6 验收

- smoke_sd_delivery.py：创建→超发 400→ship（库存扣+流水+订单 SHIPPED）→签收→开票→超开 400→issue→应收出现→reset 复位（≥12 项断言）
- 全门禁：本体双校验 / alembic / pytest / parity / tsc / 双构建 / mock-rbac / 行为探针

## 四、P1 批次：应付闭环 + 收款核销 + 账龄（应收应付双闭环）

### 4.1 本体建模（4 实体 + 2 枚举）

| 实体 | 表 | 说明 |
|---|---|---|
| `SupplierInvoice` 采购发票 | supplier_invoices | invoice_number(PI 前缀)、purchase_order_number(FK)、supplier_id、amount、tax_amount、status(SupplierInvoiceStatus)、invoice_date；三单匹配：Σ发票行挂 PO 行，校验 ≤ 未收量×单价 |
| `SupplierPayment` 付款单 | supplier_payments | payment_number(PAY 前缀)、supplier_id、amount、payment_date、method(TRANSFER/CASH/BILL)、status(DRAFT/PAID/CANCELLED) |
| `PaymentAllocation` 核销明细 | payment_allocations | payment_number(FK)、invoice_number(FK)、allocated_amount（一单多票核销） |
| `Receipt` 收款单 | receipts | receipt_number(RC 前缀)、customer_id、amount、method、status；核销明细复用 `PaymentAllocation`（加 direction 字段或分表——**分表 `receipt_allocations`** 更清晰） |

**枚举**：`SupplierInvoiceStatus`(DRAFT/CONFIRMED/CANCELLED)、`PaymentMethod`(TRANSFER/CASH/BILL)

### 4.2 业务规则

- 采购发票 CONFIRM 后：AP 视图口径升级为「已确认发票 − 付款核销」（替换现在的收货估算口径；收货暂估保留为未开票应付列）
- 付款单 PAID：按核销明细冲减发票已付额；发票足额核销 → PARTIALLY_PAID/PAID 联动
- 收款单同构冲减销售发票 `received_amount`，应收台账流水记 RECEIPT
- 账龄：未核销余额按发票日期分 0-30/31-60/61-90/90+ 四段

### 4.3 端点 / 前端

- 后端：`/purchase/supplier-invoices`(CRUD+confirm)、`/purchase/payments`(创建/支付/取消/核销)、`/sd/receipts`(同构)；`/purchase/ap-view` 升级、`/sd/receivables` 升级（含核销后口径）
- 前端：采购发票页（三单匹配视图）、付款单页（核销对话框）、收款单页；应收/应付台账页升级（账龄列 + 核销进度）
- 菜单：采购与库存 +2（采购发票、付款单）；销售与分销 +1（收款单）——分组膨胀时「采购发票/付款」可并入应付台账页 Tabs

### 4.4 验收

smoke_finance_loop.py：三单匹配→确认→付款核销→发票 PAID→AP 递减；收款→应收递减→发票 PAID→账龄变化（≥14 项）。

## 五、P2 批次：轻量总账 + 自动分录引擎（三线汇合）

| 实体 | 表 | 说明 |

### 5.2 自动分录映射表（引擎核心，配置化常量 `backend/services/finance/gl_rules.py`）

| 业务事件（source_type） | 借方 | 贷方 | 金额口径 |
|---|---|---|---|
| SALES_INVOICE_ISSUED | 应收账款(1122) | 主营业务收入(6001) | 发票金额 |
| SALES_DELIVERY_SHIPPED | 主营业务成本(6401) | 库存商品(1405) | 发货量 × 物料标准成本（衔接成本域 standard_cost） |
| SUPPLIER_INVOICE_CONFIRMED | 库存商品(1405) | 应付账款(2202) | 发票金额 |
| SUPPLIER_PAYMENT_PAID | 应付账款(2202) | 银行存款(1002) | 付款金额 |
| RECEIPT_PAID | 银行存款(1002) | 应收账款(1122) | 收款金额 |
| MATERIAL_ISSUE / STOCK_ADJUST | 生产成本-直接材料(5001) | 库存商品(1405)（调整反向） | 领料量 × 标准成本（补记历史口径由成本域已有数据回补，仅 P2 后增量） |

| PURCHASE_RECEIPT | （不单独入账，与发票合并——demo 简化：收货暂估省略，发票即入账） | — | — |

> 科目表种子：8-12 个一级科目 + 常用二级；映射表为 Python 常量（demo 不做科目映射 UI）。
> **分录引擎**：`GlEngine.post(db, source_type, source_ref, lines)`——单据动作处调用；POSTR 日志 + 幂等（source_type+source_ref 唯一，重复调用跳过）。

### 5.3 端点 / 前端

- 后端：`/finance/accounts`、`/finance/journal-entries`(列表/详情/过账)、`/finance/trial-balance`(科目余额表)、`/finance/periods`；P0/P1 单据动作处挂 GlEngine.post

## 八、已知坑预防清单（每批开工前过一遍）

1. **路由顺序**：固定路径（/performance、/refs）必须注册在路径参数（/{code}）之前——后端与 mock 双端。
2. **同事务连续生成单号**：每次 add 后 `flush()`，否则 max 查不到未落库行导致重号。
3. **探针/脚本 sys.path**：必须注入项目根，否则 `backend` 被 PYTHONPATH 解析到 `D:\CubeGalaxy` 旧副本（TestClient 结果全错且难察觉）。
4. **新表入库**：`create_all` 后跑 `alembic check` 保持 EXIT=0；新实体全字段带 comment（与建表一致）。
5. **SHACL**：sh:in 值顺序与 mappings 完全一致；新属性必须先在 erp-ontology.ttl 声明（Check6）；demo.ttl 实例须双类型（业务类+顶层范畴）。
6. **reset 卫生**：运行时表进清理列表；种子按「备注标记/引用单据」幂等判重；SHIPPED 等带副作用的种子必须同步扣库存+写流水，保证 reset 后三线自洽。
7. **mock 同构**：快照版本号递增；parity 扩项；`check:mock-rbac` + 一次性行为探针（esbuild）。
8. **大文件写入**：write 后验证末尾（曾出现传输损坏）。
9. **数字前缀规划**：DK(发货)/INV(销售发票)/PI(采购发票)/PAY(付款)/RC(收款)/AR(应收流水)/JE(凭证)——与 SHACL pattern 一并定义。
